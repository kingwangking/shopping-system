# 架构设计（初版）

## 1. 设计目标
本项目当前阶段目标是建设“最简单订单系统”，聚焦订单记录、查询、统计三项能力。

架构选择遵循两项原则：
- 从整体到局部：先定义整体结构与边界，再逐步细化实现。
- 问题导向 DDD：围绕真实业务问题建模，避免脱离场景的过度设计。

为此，项目采用 DDD 思路下的 Clean 架构，并使用常见 Web 项目组织方式。

## 2. 架构风格
采用分层解耦的 Clean 架构，保证核心业务规则独立于框架、数据库和接口协议。

### 2.1 分层说明
- Domain（领域层）
  - 定义订单核心业务模型与规则。
  - 包含实体、值对象、领域服务、仓储接口。
  - 不依赖外部框架与基础设施实现。

- Application（应用层）
  - 编排具体业务用例（Use Case）。
  - 负责事务边界、权限校验（如有）、参数组织。
  - 依赖 Domain 抽象，不依赖具体基础设施实现。

- Infrastructure（基础设施层）
  - 提供技术实现细节，如数据库访问、仓储实现、日志、配置。
  - 实现 Domain/Application 定义的接口。

- Interfaces（接口层 / Web 层）
  - 对外提供 HTTP API。
  - 负责请求接收、参数校验、DTO 转换、响应封装。
  - 调用 Application 层用例，不直接操作数据库。

### 2.2 依赖方向规则
依赖必须“向内”流动：
- Interfaces -> Application -> Domain
- Infrastructure -> Application / Domain（实现接口）
- Domain 不依赖其他层。

## 3. 当前阶段领域边界
当前只建立一个核心子域：订单（Order）。

### 3.1 纳入范围
- 订单记录（新增订单）
- 订单查询（按条件检索）
- 订单统计（数量、金额等基础统计）

### 3.2 暂不纳入范围
- 商品中心
- 库存管理
- 营销能力
- 支付闭环
- 复杂审批或工作流

## 5. 第一阶段最小用例映射
- CreateOrder（记录订单）
- QueryOrders（查询订单）
- GetOrderStatistics（统计订单）

说明：第一阶段先完成“可用闭环”，再逐步补充复杂规则与性能优化。

## 6. 演进策略
- 先保证分层边界清晰，再迭代业务细节。
- 新增功能优先进入既有层次，不随意穿层。
- 当业务复杂度提升时，再考虑拆分更多限界上下文。

## 7. 文档结论
项目采用 DDD 思路下的 Clean 架构与 Web 结构是合理且可执行的。该方案既能支撑当前“最简订单系统”的快速落地，也为后续演进至更完整系统保留了结构弹性。
